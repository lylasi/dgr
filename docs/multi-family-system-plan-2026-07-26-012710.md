# 多家庭、系统管理员与老板账号改造计划

> 文档状态：实施与验收完成（阶段一至阶段五均已完成）
>
> 创建时间：2026-07-26 01:27:10 +08:00（Asia/Shanghai）
>
> 适用项目：PEN子打工人

## 1. 背景与目标

当前系统采用单管理员模式：管理员密码保存在环境变量中，管理员可以管理数据库中的全部打工人、任务、奖励、计时和账本。该模型适用于单个家庭，但无法安全地让几个家庭共同使用同一个部署实例。

本次规划的目标是：

- 保持私有化、低用量、SQLite 单实例的简单部署方式。
- 支持多个家庭在同一套系统中使用，并保证家庭之间的数据隔离。
- 将当前环境变量管理员调整为唯一的“系统管理员”。
- 为各家庭建立数据库中的“老板”账号，一个家庭可以有多个老板。
- 系统管理员只负责家庭和老板账号的简单管理，不参与日常家庭业务。
- 老板负责所属家庭中的小朋友、任务、奖励、计时与账本。
- 保留当前方便的角色切换体验，让老板可以快速进入本家庭某个小朋友的页面进行陪同或代操作。
- 为未来跨家庭社区、换物和时间关联预留清晰边界，但当前不实现社区功能。

本设计面向几个熟悉家庭的私有使用，不按公开互联网 SaaS、海量用户或复杂企业权限系统设计。

## 2. 总体模型

系统形成三个层级：

```text
系统管理员（环境变量密码）
    └── 管理家庭和老板账号
            └── 老板管理所属家庭
                    └── 小朋友使用任务、时间与奖励
```

数据关系为：

```text
系统管理员
    ├── 家庭 A ──< 老板账号 >── 小朋友、任务、奖励、账本
    ├── 家庭 B ──< 老板账号 >── 小朋友、任务、奖励、账本
    └── 家庭 C ──< 老板账号 >── 小朋友、任务、奖励、账本
```

系统继续使用单个 SQLite 数据库。多家庭不是通过多个数据库实现，而是通过稳定的 `family_id` 建立家庭数据边界。

## 3. 身份与职责

### 3.1 系统管理员

系统管理员继续使用部署环境变量中的唯一密码。建议把变量从 `ADMIN_PASSWORD` 更名为：

```dotenv
SYSTEM_ADMIN_PASSWORD=
```

升级过渡期可以兼容读取旧的 `ADMIN_PASSWORD`，稳定后再移除旧变量。

系统管理员负责：

- 创建、编辑、启用或停用家庭。
- 创建、编辑、启用或停用老板账号。
- 重置老板密码。
- 将老板绑定到家庭或解除绑定。
- 查看家庭数、老板数、小朋友数和最近活跃时间等简单系统概况。
- 处理账号无法登录、家庭归属配置错误等维护问题。
- 将来管理全局社区的启停、安全规则及异常账号。

系统管理员默认不负责：

- 发布或审核家庭任务。
- 日常调整小朋友余额。
- 管理家庭奖励模板和消耗项目。
- 以某位老板或小朋友的名义执行操作。
- 默认查看小朋友照片、任务详情、余额明细或家庭内部备注。

第一阶段不实现系统管理员“协助进入家庭”。未来若增加，必须要求填写协助原因、醒目标注协助模式，并记录所有访问和修改，不能伪装成家庭老板。

### 3.2 老板

老板是保存在数据库中的正式账号，使用唯一登录名和密码登录。登录名用于认证，显示名用于界面和操作记录，例如登录名为 `linus`，显示名为“爸爸”。

老板可以自行修改账号默认显示名称，也可以为当前家庭设置独立昵称。家庭昵称存在时优先显示；没有设置时回退账号默认名称。登录名仍由系统管理员维护，密码可由老板验证当前密码后自行修改，也可在忘记密码时由系统管理员重置。已经产生的审计记录保留操作发生时在该家庭使用的有效名称快照，不随之后改名而重写。

老板负责所属家庭的日常业务：

- 创建、编辑和停用小朋友，设置或重置小朋友 PIN。
- 管理小朋友头像、每日奖励和每日随机券设置。
- 发布、编辑、关闭、复制和分配任务。
- 审核任务及小朋友自主奖励申报。
- 代为管理计时、快速补录奖励和调整余额。
- 管理奖励模板、奖励券和消耗项目。
- 查看本家庭任务、奖励、计时、账本和操作记录。
- 将来决定本家庭是否参与社区，以及批准小朋友的换物或时间关联行为。

一个家庭可以绑定多个老板；一个老板也可以绑定多个家庭。如果老板只有一个家庭，登录后直接进入；如果有多个家庭，登录后先选择当前家庭，也可以在后台安全切换。

当前不设计复杂的老板权限点，也不设计“老板只能管理某几个小朋友”。同一家庭的老板拥有相同的家庭业务管理能力。新增或移除老板统一交由系统管理员处理。

### 3.3 小朋友（打工人）

小朋友继续作为家庭内业务角色，而不是老板账号的一种权限。保留当前独立 PIN、长期设备授权和角色选择体验。

小朋友只能访问：

- 自己所属家庭的公开角色入口。
- 自己的任务、计时、余额、交易和奖励。
- 所属家庭启用的消耗项目。
- 将来经过老板批准的社区公开身份和社区功能。

第一阶段一个小朋友只属于一个家庭。

## 4. 老板快速进入小朋友页面

### 4.1 产品结论

允许，并应保留类似当前角色切换页的快速体验。老板登录后，可以在当前家庭的角色列表中一键进入任意小朋友页面，不需要重新输入该小朋友的 PIN。

该功能定义为“老板陪同/代操作模式”，不是老板冒充小朋友登录。

建议流程：

```text
老板后台
    → 打开角色切换页
    → 选择本家庭小朋友
    → 进入该小朋友页面（老板代操作）
    → 一键返回老板后台
```

### 4.2 界面要求

- 页面持续显示“爸爸正在代小明操作”之类的醒目标识。
- 保留清晰的一键“返回老板后台”。
- 切换列表只显示当前家庭的小朋友。
- 老板从一个小朋友切到另一个小朋友时，不要求输入小朋友 PIN。
- 小朋友本人从家庭入口进入时，仍需按既有规则输入自己的 PIN。

### 4.3 身份和审计要求

会话身份需要区分：

```text
system_admin
boss
worker
boss_as_worker
```

`boss_as_worker` 至少保存：

- 真实操作者 `boss_id`。
- 当前家庭 `family_id`。
- 当前代操作对象 `worker_id`。

代操作产生的记录必须保留真实操作者。例如：

```text
爸爸代小明领取任务
爸爸代小明开始计时
爸爸代小明提交任务
```

不能把这些操作记成“小明本人”，也不能继续笼统记录为 `admin`。小朋友通过自己的 PIN 登录后执行的操作，才记录为小朋友本人。

### 4.4 代操作边界

老板可以代操作普通家庭业务，例如领取、计时、暂停、提交、取消任务，以及使用普通时间券。

以下敏感操作不能因为进入小朋友页面就自动获得“小朋友本人确认”的含义：

- 实物券确认收到。
- 未来社区换物的儿童本人确认。
- 未来跨家庭交换或社区积分兑换。
- 明确要求小朋友本人同意的其他动作。

这类动作应根据业务含义要求小朋友 PIN、老板二次确认或双方家庭确认。

## 5. 简化数据模型

### 5.1 新增主要表

#### `families`

建议字段：

```text
id
name
timezone
status
entry_code
created_at
updated_at
```

`entry_code` 应使用不可猜测、可轮换的随机值，用于生成家庭入口或二维码，不使用家庭名称作为安全凭证。

当前实现会把完整家庭入口链接生成为 SVG 二维码。二维码只承载链接，不是登录凭证；扫码进入角色列表后，小朋友仍需输入自己的 PIN，老板仍需使用老板账号登录。

`timezone` 字段为旧数据和现有业务计算保留，但私有部署不提供逐家庭时区配置。新家庭自动采用服务器统一的 `APP_TIMEZONE`，系统维护界面不再要求系统管理员重复填写时区。

#### `boss_accounts`

建议字段：

```text
id
username
display_name
password_hash
auth_version
is_active
created_at
updated_at
```

老板密码使用现有可靠的密码哈希方式保存，不保存明文。老板自行修改时必须验证当前密码；修改或由系统管理员重置时递增 `auth_version`。自助修改会刷新当前设备的授权并使其他设备失效，系统管理员重置则使全部旧授权失效。

#### `family_bosses`

建议字段：

```text
family_id
boss_id
display_name_override
created_at
```

使用 `(family_id, boss_id)` 唯一约束。`display_name_override` 可为空；有效名称按“家庭昵称优先、账号默认名称兜底”计算。当前不增加 `owner/admin` 权限层级。

### 5.2 现有数据的家庭归属

以下可被接口直接查询或操作的主要对象应直接保存 `family_id`：

- `workers`
- `tasks`
- `task_assignments`
- `transactions`
- `reward_requests`
- `consumption_activities`
- `reward_definitions`
- `worker_reward_items`
- `audit_logs`
- `app_settings`

纯粹依附父对象的内部明细或快照，可以通过父对象确定家庭，例如头像图片、计时片段、任务奖励快照和奖励模板图片。若某个此类对象以后开放独立接口，则应在接口中通过父对象检查家庭，或再补充 `family_id`。

家庭设置不能继续使用全局唯一的 `app_settings.key`，应改为 `(family_id, key)`；否则一个家庭修改奖励系统开关会影响其他家庭。

### 5.3 操作者记录

原有只写 `admin` 的操作者字段不足以支持多个老板。新记录应能表达：

```text
actor_type: system_admin | boss | worker | system
actor_id: 老板或小朋友 ID，系统操作可为空
actor_name_snapshot: 操作发生时的显示名称
acting_for_worker_id: 老板代操作时的小朋友 ID，可为空
```

历史记录中的 `admin` 不强行伪造具体老板，迁移后显示为“旧版管理员”。

## 6. 登录、会话与入口

### 6.1 登录入口

建议逻辑入口：

```text
/              家庭入口与小朋友角色选择
/boss/login    老板登录
/system/login  系统管理员登录
```

实际路由可在实现阶段结合当前界面调整。系统管理员入口不需要在儿童首页突出展示。

### 6.2 会话上下文

建议表达为：

```text
系统管理员：{ type: system_admin }
老板：      { type: boss, bossId, familyId }
小朋友：    { type: worker, workerId, familyId }
老板代操作：{ type: boss_as_worker, bossId, workerId, familyId }
```

当前私有化场景可以继续使用签名 HttpOnly Cookie，不要求立即引入数据库 Session、邮件登录、找回密码和设备管理。

老板的每次请求仍必须检查：

1. 老板账号存在且启用。
2. Cookie 中的 `auth_version` 仍有效。
3. 老板仍通过 `family_bosses` 属于当前家庭。
4. 目标业务对象属于当前家庭。

因此，即使旧 Cookie 尚未过期，老板被停用、密码被重置或家庭关系被解除后也不能继续访问。

### 6.3 家庭入口

小朋友不能再从公共启动接口看到系统中的全部家庭和全部小朋友。建议家庭使用随机入口码或二维码：

```text
家庭链接/二维码 → 当前家庭角色列表 → 选择小朋友 → 输入 PIN
```

角色卡继续避免展示余额等隐私信息。头像和奖励图片接口也必须检查家庭访问上下文，避免通过猜测或泄露的 UUID 跨家庭读取儿童图片。

## 7. 权限与家庭隔离规则

家庭隔离是本次改造中不能省略的安全要求。老板的每一个读取和修改操作都必须限定当前 `family_id`。

不允许仅按外部传入的 ID 查询：

```sql
SELECT * FROM task_assignments WHERE id = ?
```

必须同时限定家庭，或者通过可靠关联验证：

```sql
SELECT * FROM task_assignments
WHERE id = ? AND family_id = ?
```

其他家庭的对象应统一按“未找到”处理，避免向调用者泄露该对象是否存在。

建议将接口职责拆分为：

```text
/api/system/*   系统管理员：家庭和老板账号管理
/api/boss/*     老板：当前家庭业务
/api/worker/*   小朋友本人业务
```

老板代操作可通过老板接口携带目标 `worker_id`，或者建立清晰的代操作上下文；不能借用小朋友本人授权绕过审计。

跨家庭分配任务、审核、调整余额、发券、读取图片和切换角色都必须失败。

## 8. 现有数据迁移方案

升级现有部署时：

1. 升级前完整备份 SQLite 数据库。
2. 创建一个默认家庭，例如“我的家庭”。
3. 将现有小朋友、任务、分配、奖励、计时、账本、消耗项目和设置归入该家庭。
4. 保留原环境变量密码，但将身份语义改成系统管理员。
5. 系统管理员首次进入后创建至少一个老板账号，并绑定默认家庭。
6. 后续家庭日常管理改为使用老板账号。
7. 原有 `admin` 历史操作显示为“旧版管理员”。
8. 新操作记录具体老板、小朋友、系统管理员或系统任务。
9. 迁移后校验表记录数量、任务状态、奖励券状态和账本余额。
10. 执行外键检查，并验证不同家庭之间不存在错误关联。

迁移应使用版本化数据库 migration，并允许旧库直接升级；不要求用户手工修改数据库。

## 9. 系统管理后台

系统管理员登录后进入独立、精简的系统后台，第一阶段包括：

- 系统概况。
- 紧凑家庭列表，以及弹窗式新增、编辑、启用和停用；家庭入口和二维码只在编辑弹窗中展开。
- 可按显示名、登录名或家庭搜索的紧凑老板账号列表；新增和编辑使用弹窗，家庭绑定与密码重置只在编辑弹窗中展开。
- 老板与家庭绑定管理。
- 基础审计记录。

系统管理员默认只看统计和归属，不直接加载所有家庭的任务、账本、头像和奖励详情。

原有管理员业务页面调整为老板的家庭后台，主要业务交互尽量复用。

## 10. 未来社区与换物预留

社区应建立在家庭层之外，不能破坏家庭私有边界：

```text
家庭私有域
  家庭 ──< 小朋友 ──< 任务、家庭时间、奖励与账本

社区共享域
  小朋友 ──< 社区公开身份 >── 社区
                              ├── 换物信息
                              ├── 交易协商
                              ├── 双方家庭确认
                              └── 社区积分
```

未来应单独建立 `community_profiles`，只公开社区昵称、社区头像、简介、换物列表和必要的信誉信息，不直接公开真实姓名、家庭任务、家庭余额、PIN、账本或老板备注。

### 10.1 换物建议演进顺序

1. 先实现物品发布和交换意向，不关联时间。
2. 由双方小朋友表达意向，双方家庭老板最终确认。
3. 再尝试“时间承诺”，只记录约定与完成情况，不直接跨家庭转移余额。
4. 如果确实需要跨家庭经济体系，再建立独立社区积分。

### 10.2 家庭时间不能直接等价跨家庭流通

不同家庭的每日奖励、任务奖励和使用规则不同，家庭 A 的 60 分钟与家庭 B 的 60 分钟不一定具有相同获得成本。直接互转会产生不公平和套利。

因此建议长期保持：

```text
家庭时间：家庭内部资产，由本家庭规则管理
社区积分：跨家庭社区资产，由社区统一规则管理
```

两者未来可以有限关联，例如家庭设置每周参与上限、完成社区服务后由老板确认发放家庭时间，或社区积分兑换家庭时间必须经过老板批准。当前版本只预留小朋友稳定 ID、家庭边界、真实操作者和家庭确认能力，不建立社区数据表。

## 11. 实施阶段建议

### 阶段一：数据库家庭边界

- 新增家庭、老板账号和家庭老板关系。
- 为主要业务对象增加 `family_id`。
- 将现有数据迁入默认家庭。
- 增加必要索引、唯一约束和家庭关联校验。

### 阶段二：系统管理员与老板认证

- 将环境变量管理员调整为系统管理员。
- 建立老板数据库密码登录。
- 调整 Session 身份和授权版本校验。
- 增加系统管理接口和老板家庭接口。

### 阶段三：业务服务家庭化

- 依次改造小朋友、任务、计时、审核、账本、奖励和设置查询。
- 所有服务函数显式接收家庭与操作者上下文。
- 操作记录写入具体老板和代操作对象。

### 阶段四：界面与快速角色切换

- 建立系统管理后台。
- 将原管理员页面调整为老板后台。
- 增加老板家庭选择。
- 保留角色选择页并实现老板代操作模式。

## 12. 验收标准

- 系统管理员可以管理家庭、老板账号及其绑定关系。
- 系统管理员默认不进入家庭日常业务。
- 老板只能看到和操作当前家庭的数据。
- 一个家庭支持多个老板，一个老板支持多个家庭。
- 小朋友只能进入自己的家庭并访问自己的业务数据。
- 老板可以修改账号默认名称、当前家庭昵称、自己的登录密码和当前家庭名称；名称历史审计快照保持不变。
- 同一老板在不同家庭可以显示不同昵称；未设置昵称的家庭自动使用账号默认名称。
- 老板自助修改密码后当前设备保持登录，其他设备的旧授权立即失效；忘记密码仍可由系统管理员重置。
- 老板和系统管理员都可以查看、复制、扫码或轮换家庭入口；轮换后旧链接和旧二维码立即失效。
- 老板可以快速进入本家庭小朋友页面，无需小朋友 PIN。
- 老板代操作有醒目标识，并记录真实老板和目标小朋友。
- 老板不能通过代操作获得“小朋友本人确认”的效果。
- 家庭 A 持有家庭 B 的对象 ID 时，无法读取、修改、审核、发券或读取图片。
- 原有小朋友、任务、余额、交易、计时和奖励数据能够完整迁移。
- 现有任务、奖励、计时和账本核心规则保持不变。
- SQLite、单实例和当前私有化部署方式可以继续使用。

## 13. 当前明确不做

- 公开注册。
- 邮件邀请、邮件验证和自助找回密码。
- 数据库 Session 和远程设备管理。
- 多位系统管理员。
- 老板复杂角色和细粒度权限点。
- 只允许老板管理指定几个小朋友。
- 系统管理员日常代管家庭。
- PostgreSQL、微服务或多实例部署。
- 社区、换物、社区积分或跨家庭时间转账。
- 小朋友携带完整历史业务数据跨家庭迁移。

这些能力可以在实际需要出现后单独设计，不应增加当前几个家庭私有使用的复杂度。

## 14. 已确认的关键决策

1. 使用单实例、单 SQLite 支持几个私有家庭。
2. 环境变量密码对应唯一系统管理员。
3. 家庭管理者改称“老板”，账号保存在数据库中。
4. 系统管理员管理家庭和老板，老板管理家庭业务。
5. 一个家庭可以有多个老板，一个老板可以属于多个家庭。
6. 暂不引入复杂老板权限。
7. 家庭是所有现有业务数据的安全边界。
8. 老板可以快速进入小朋友页面，但必须采用可审计的代操作模式。
9. 未来社区与家庭私有数据分层，家庭时间不直接跨家庭等价流通。
10. 本文档是需求、实施和验收基线；功能严格按阶段推进，未到阶段的能力不得提前假装开放。
